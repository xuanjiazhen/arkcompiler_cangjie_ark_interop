## 意见 1：线程错误分类 — THREAD_MISMATCH 与运行时已销毁应区分

> **原文**：若编译器无法静态确定线程安全性，则在运行时通过 JSFunc 自动进行线程切换调度。调度失败（如 ArkTS 运行时已销毁）时抛出 THREAD_MISMATCH 错误。
>
> **意见**：ArkTS运行时已销毁抛出 JSObjectUseAfterFree

**答复**：已采纳。§5.3 将运行时错误拆分为两类：

- **`THREAD_MISMATCH`（34300004）**：线程不匹配导致不可执行时抛出
- **`REFERENCE_BEYOND_REACH`（34300003）**：ArkTS 运行时已销毁或目标引用不可达时抛出

§12.2 错误表同步更新，`REFERENCE_BEYOND_REACH` 独立列出并覆盖 §5.3、§13.5、§14 三个触发场景。附录 A 错误码定义表已更新描述。

## 意见 2：空元组与 Unit 的关系

> **意见**：空元组仓颉也不支持，为什么又对应成 Unit

**答复**：已采纳。§5.4 元组限制条款第 3 项明确：

> "仓颉中的 `()` 是 `Unit` 的表达形式而非空元组；映射规则见 4.4 节。"

第 4 项补充："仓颉元组至少需要两个元素，因此不存在 0 元素或 1 元素元组映射。"

两者关系：`()` 在仓颉语义上是 `Unit` 类型，不是空元组，不走元组映射路径，而是走 §4.4 空值类型映射（`Unit` → `void`/`undefined`）。

## 意见 8：可导出类型概念与依赖传递

> **意见**：被标记声明，如果依赖其他声明，被依赖的声明也需要被标记的？或者说有个可导出类型的概念，包括基础类型，以及被标记的类型

**答复**：已采纳。§2.5 引入"可导出类型（Exportable Type）"概念，定义为：

第 7 项明确传递性："若导出声明引用了用户定义类型，则被引用类型也必须可导出；否则编译报错。"

## 意见 10：回调跨线程存储的报错阶段与错误类型

> **意见**：这个场景是在什么阶段报错？往全局变量存的时候，还是跨线程共享的时候；编译报错只针对编译器能判断的场景，不能判断的场景依赖运行时切换或报错，对吧；THREAD_MISMATCH 是异常吧

**答复**：已全面采纳。§5.3 函数类型改为三层递进处理表：

| 场景 | 说明 |
|------|------|
| 回调在 `spawn` 创建的新线程中调用 | 编译器插入自动线程切换胶水代码 |
| 回调传递给未标记 `@Interop[ArkTS]` 的仓颉函数 | 编译器无法追踪最终调用线程，给出警告 |
| 回调存储到全局变量后在其他线程读取调用 | 若可静态判定跨线程则编译报错；不可判定则运行时检查 |

以及运行时兜底规则：

- `THREAD_MISMATCH` → **异常**（已全文统一用"异常"而非"错误"）
- `REFERENCE_BEYOND_REACH` → 异常（独立于 THREAD_MISMATCH）

报错阶段：编译器能判断的场景在编译期报错，不能判断的场景在运行时由 `JSFunc` 自动线程切换处理，切换失败抛异常。

## 意见 11：sealed 修饰符到底支不支持

> **意见**：这段话没说太清楚，到底支不支持 seal

**答复**：已采纳。§6.6 改为清晰的分点表述：

> 关于 `sealed` 修饰符：仓颉的 `sealed` 语义是"仅允许同包继承"，该语义无法在 ArkTS 侧强制表达。
>
> - **`sealed open class`**：允许导出，ArkTS 侧可继承；但仓颉的同包继承限制在 ArkTS 侧不生效，编译器给出警告。
> - **`sealed class`（非 `open`）**：可导出为不可继承类，ArkTS 侧不可继承。
>
> 若业务需要严格限制继承范围，建议避免将 `sealed open` 类导出到 ArkTS。

结论：**支持导出，但 sealed 的同包限制在 ArkTS 侧无法强制执行**。

## 意见 13：全局 var 的可变语义

> **意见**：可变的情况，是基于引用吗

**答复**：已采纳。§10.1 增加了 var 跨语言读写机制说明：

## 意见 14：JSInteropType 约束在仓颉侧调用时是否生效

> **意见**：这个方法在仓颉侧被调用时，T 需要满足 JSInteropType 的约束吗

**答复**：已采纳。§11.2 明确约束作用域：

> "`JSInteropType` 约束仅在跨语言边界生效：
> - ArkTS 调用该导出函数时：由 `.d.ts` 可表达约束参与 ArkTS 编译期检查，其余约束由运行时胶水代码检查

结论：仓颉侧直接调用时 **T 不需要额外满足 `JSInteropType` 约束**，仅在跨边界调用时生效。

## 意见 15：约束检查是编译错误还是运行时错误

> **意见**：编译错误能搞定吗，因为 arkts 编译我们控制不了，我们只能在注解处理逻辑里去判断，实际是运行时错误

**答复**：已采纳。§11.2 修改为：

> "ArkTS 调用该导出函数时：由 `.d.ts` 可表达约束参与 ArkTS 编译期检查，其余约束由运行时胶水代码检查"

以及：

> "例如，ArkTS 调用 `identity(someValue)` 时，`someValue` 需满足可跨边界传递条件；若编译期无法完全判定，则运行时检查失败时抛出 `TYPE_MISMATCH` 异常。"

区分两层：`.d.ts` 中 `extends` 能表达的约束走 ArkTS 编译器检查；不能表达的依赖运行时胶水代码校验。

## 意见 16：泛型约束映射处理

> **意见**：泛型约束会怎么处理？

**答复**：已采纳。§11.2 增加约束映射规则表与补充规则：

| 仓颉约束 | ArkTS 约束 |
|---------|-----------|
| `T`（自动蕴含 `JSInteropType`） | `<T>`（不体现） |
| `T <: SomeClass` | `<T extends SomeClass>` |
| `T <: InterfaceA & InterfaceB` | `<T extends InterfaceA & InterfaceB>` |

补充规则：
- 约束中引用的类型本身必须可导出
- 无法在 ArkTS 类型系统中表达的仓颉约束在导出时退化为 `<T>`，编译器给出警告，运行时继续校验

## 意见 22：ArkTS 继承仓颉类的完整性

> **意见**：这个功能想清楚了吗？特别是继承以后能不能 override 里面的 open 函数

**答复**：已采纳。§6.7 大幅补充：

**Override 规则**：
- ArkTS 子类可重写仓颉 `open` 方法
- 仓颉侧多态调用时，对象为 ArkTS 子类实例则通过胶水层分派到 ArkTS 侧重写实现
- ArkTS 子类中的 `super.method()` 调用会回落到仓颉父类实现

**限制表**（7 项）：

| 限制 | 说明 |
|-----|------|
| 只能继承 `open` 类 | 非 `open` 类不可被 ArkTS 继承 |
| 只能重写 `open` 方法 | 非 `open` 方法不可重写 |
| 仓颉侧不可见子类类型 | 仓颉代码中无法使用 ArkTS 子类类型 |
| 子类新增成员仓颉不可访问 | 仓颉无法访问 ArkTS 子类新增的属性和方法 |
| `protected` 成员不可访问 | 当前不支持跨语言 `protected` 访问 |
| 必须调用 `super()` | 编译器生成的基类 `constructor` 中包含仓颉对象初始化逻辑 |
| 多层混合继承受限 | 当前版本不保证 ArkTS→仓颉→ArkTS 的多层混合继承链行为 |

## 意见 24：ArkTS 调用仓颉泛型函数的实现可行性

> **意见**：ArkTS 调用仓颉时，对于泛型函数的处理，在实现上能搞定不？胶水代码里要怎么填入那个 T 参数呢？

**答复**：已采纳。§11.7 运行时行为增加实现说明：

ArkTS/TypeScript 运行时做类型擦除，泛型信息不保留。胶水代码通过运行时推断类型实参：

- **基础类型**：通过 `typeof` 推断（如 `typeof value === 'number'`）
- **class 实例**：通过 `instanceof` 推断
- **interface/struct**：通过结构性检查推断（检查所需属性和方法是否存在）
- **嵌套泛型**：递归检查内层类型

对性能敏感路径，编译器可为常见类型参数组合生成特化胶水逻辑；无法推断时退回通用 `JSValue` 路径并在仓颉侧做最终校验。

**答复**：已采纳。§14 概述增加前置条件段：

> "前置条件：仓颉调用 ArkTS 需要存在可用的 ArkTS 运行时。
> - **嵌入场景（主流）**：由 ArkTS 入口拉起应用，仓颉作为被调用方，复用已初始化运行时
> - **独立场景**：由仓颉入口拉起应用，需先初始化 ArkTS 运行时（见 14.3 节）
>
> 若在运行时未初始化或已销毁的状态下调用 `foreign` 声明，抛出 `REFERENCE_BEYOND_REACH` 异常。"

新增 §14.3 ArkTS 运行时初始化策略补充了仓颉独立入口场景的处理方式。

## 意见 26：仓颉调用 ArkTS 泛型的实现可行性

> **意见**：同理，仓颉调用 ArkTS 时，对于泛型函数的处理，在实现上能搞定不？胶水代码里要怎么填入那个 T 参数呢？

**答复**：已采纳。§19 泛型章节增加实现说明：

> "仓颉调用 ArkTS 泛型时，仓颉编译器在调用点已知类型实参，胶水层按已知类型执行入参与返回值转换：
> - 入参方向：将仓颉类型转换为 ArkTS 运行时值（如 `Int32`→`number`）
> - 返回方向：按调用点类型实参做结果校验与转换
>
> ArkTS 运行时本身不保留泛型实参信息，因此类型安全由仓颉侧编译器与胶水层共同保证。"

与意见 24（ArkTS→仓颉方向）不同，仓颉→ArkTS 方向更简单：仓颉编译器在调用点已知具体类型实参，无需运行时推断，直接按已知类型生成特化的转换逻辑。
