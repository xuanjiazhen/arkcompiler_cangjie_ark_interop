**审视范围**：§18, §19, §20.1, §21.1–§21.2
**日期**：2026-04-11

## 一、红军攻击意见（用户/架构师角色）

### 攻击 8-1：§18 全局声明访问过于简略

§18 整章仅有两行声明示例，缺少关键说明：
- `foreign let` 的值是何时获取的——首次访问时（惰性）还是初始化时（急切）？
- `foreign var` 的写入行为——仓颉侧写入后 ArkTS 侧何时可见？是否有同步延迟？
- `foreign const` 是否支持？

**严重程度**：高  
**影响范围**：§18

### 攻击 8-2：§19 泛型的"编译器在调用点已知类型实参"不适用于动态分派场景

§19 说"仓颉编译器在调用点已知类型实参，胶水层按已知类型执行入参与返回值转换"。但如果 foreign 泛型类实例被存储到 `Collection<JSInteropType>` 后擦除了类型信息，后续从集合取出时编译器不知道原始类型实参。这种场景下类型安全如何保证？

**严重程度**：中  
**影响范围**：§19

### 攻击 8-3：§20.1 JSException 异常类型层次不完整

§20.1 只定义了 `JSException`、`JSTypeException`、`JSRangeException` 三种。ArkTS/JavaScript 的错误层次还包括 `ReferenceError`、`SyntaxError`、`URIError`、`EvalError`。虽然 §12 的仓颉→ArkTS 方向不需要（仓颉没有对应异常），但 ArkTS→仓颉 方向 ArkTS 侧可能抛出这些错误。未覆盖时全部退化为 `JSException`，开发者无法精确捕获。

**严重程度**：中  
**影响范围**：§20.1

### 攻击 8-4：§20.1 JSException 的 name 属性是否足以区分未映射的错误类型

§20.1 最后一行映射表说"其他 Error 子类 → JSException，保留 message 和 stack"。但 JSException 的属性列出了 `name` 字段（"错误类型名称如 TypeError"）。依赖字符串 `name` 字段做类型判断是反模式——应尽量使用类型系统而非字符串比较。

**严重程度**：低  
**影响范围**：§20.1

### 攻击 8-5：§21.1 foreign 调用跨线程阻塞可能导致死锁

§21.1 说"若调用发生在非 ArkTS 线程，胶水代码将调用请求投递到 ArkTS 运行时线程，并阻塞当前仓颉线程等待结果返回"。如果 ArkTS 运行时线程正在等待仓颉侧完成某个操作（如回调），而仓颉侧又在等待 ArkTS 侧的 foreign 调用返回——就会形成死锁。

**严重程度**：高  
**影响范围**：§21.1, §13.3

### 攻击 8-6：§21.2 JSPromise\<T\>.get() 无超时机制的风险

§21.2 明确说"不提供超时机制"，并建议 ArkTS 侧添加超时逻辑。但如果 ArkTS 侧的 Promise 永远不 resolve（如网络永久不响应），仓颉线程将永久挂起。对于生产环境这是不可接受的。

**严重程度**：高  
**影响范围**：§21.2

### 攻击 8-7：§21.2 JSPromise 与 Future 的不对称设计增加学习成本

§21.2 的注释详细解释了 `Future<T>` 和 `JSPromise<T>` 的不对称设计原因（异步发起方不同）。虽然技术上合理，但两个不同的异步抽象（`Future<T>` 和 `JSPromise<T>`）增加了学习和使用成本。是否可以提供统一的外观（如让 `JSPromise<T>` 实现仓颉的某个标准异步接口）？

**严重程度**：中  
**影响范围**：§21.2

## 二、裁判裁决（设计者角色）

| 编号 | 判定 | 理由 |
|------|------|------|
| 8-1 | **采纳** | §18 确实过于简略。应补充值获取时机（首次访问时通过胶水代码从 ArkTS 模块读取）、写入可见性（仓颉写入通过胶水代码立即反映到 ArkTS 侧）、以及不支持 `foreign const`（ArkTS `const` 声明可通过 `foreign let` 只读访问）。 |
| 8-2 | **部分采纳** | 类型擦除后的安全性是泛型的通用问题。foreign 泛型实例被擦除后，后续访问按 `JSObject` 路径处理——与仓颉原生泛型的擦除行为一致。应增加注释说明泛型类型擦除后的行为。 |
| 8-3 | **部分采纳** | 当前三种异常类型覆盖了最常见场景。扩展完整层次可在后续版本考虑。但应明确说明未映射的 Error 子类通过 `JSException` 的 `name` 属性可识别。 |
| 8-4 | **驳回** | `name` 属性是辅助调试信息，不是用于分支逻辑的类型判断。ArkTS 的 Error 子类非常多（包括自定义 Error），不可能穷举映射。`name` 属性提供最大灵活性，开发者可根据需要检查。 |
| 8-5 | **采纳** | 死锁风险是真实的设计问题。必须在规范中明确告知此风险并提供避免死锁的指引：仓颉侧同步调用 foreign 函数时不应持有 ArkTS 回调的执行路径所需的资源。 |
| 8-6 | **部分采纳** | 永久挂起是生产环境的严重风险。但超时机制的语义复杂（超时后 Promise 仍可能 resolve）。应增加建议：使用 `spawn` + 超时取消仓颉线程的方式实现应用层超时。同时标注未来版本可考虑 `get(timeout)` 重载。 |
| 8-7 | **驳回** | 不对称是由于两种场景的本质差异导致。强行统一会引入不必要的抽象层；`JSPromise<T>` 是简单的 API（仅 `get()` 和 `isDone()`），学习成本低。保持当前设计。 |

## 三、蓝军修改方案

### 修改 8-1：§18 补充详细说明

将 §18 扩展为：

```markdown
## 18. 全局声明访问

### 18.1 foreign let / foreign var

`foreign let` 声明映射 ArkTS 模块的只读导出变量，`foreign var` 声明映射可读写导出变量。

| 声明形式 | ArkTS 对应 | 读写性 |
|---------|-----------|-------|
| `foreign let` | `export const` / `export let`（只读访问） | 仅读取 |
| `foreign var` | `export let`（读写访问） | 可读写 |

**值获取时机**：每次访问 `foreign let`/`foreign var` 时，胶水代码从 ArkTS 模块读取当前值，不进行缓存。
**写入可见性**：仓颉侧通过 `foreign var` 写入的值，由胶水代码立即同步到 ArkTS 模块侧。
**foreign const**：不单独支持 `foreign const` 声明。ArkTS `const` 导出的常量可通过 `foreign let` 以只读方式访问。
```

### 修改 8-2：§19 增加类型擦除说明
在泛型调用说明后增加："当 foreign 泛型类实例的类型参数被擦除后（如存入非泛型集合），后续访问时按 `JSObject` 通用路径处理，运行时校验取代编译期类型安全。"

### 修改 8-3：§20.1 增加未映射 Error 说明
在映射表格后增加："未在上表中列出的 ArkTS Error 子类（如 `ReferenceError`、`SyntaxError` 等）统一映射为 `JSException`，可通过 `name` 属性获取原始错误类型名称以辅助调试。后续版本可根据使用频率扩展映射粒度。"

### 修改 8-5：§21.1 增加死锁风险警告
在线程调度策略后增加：

> **死锁风险警告**：当仓颉线程通过 `foreign` 调用同步等待 ArkTS 线程返回结果，同时 ArkTS 线程正在等待该仓颉线程完成某操作（如回调执行）时，会形成死锁。
>
> **避免死锁的指引**：
> - 避免在 ArkTS 回调链路内同步调用 `foreign` 函数
> - 使用异步模式（`JSPromise<T>`）代替同步等待
> - 避免在 `foreign` 调用的返回路径上触发需要仓颉线程参与的 ArkTS 操作

### 修改 8-6：§21.2 增加超时建议
在"不提供超时机制"后修改为："不提供内建超时机制。**应用层超时建议**：可通过 `spawn` 创建独立仓颉线程调用 `get()`，外层仓颉线程设置定时器取消等待线程。未来版本考虑提供 `get(timeout: Duration)` 重载。"
