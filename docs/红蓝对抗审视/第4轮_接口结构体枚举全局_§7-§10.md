**审视范围**：§7, §8, §9, §10.1–§10.2
**日期**：2026-04-11

## 一、红军攻击意见（用户/架构师角色）

### 攻击 4-1：§7 接口方法映射为箭头函数属性改变了 this 绑定语义

§7 将接口方法 `func foo(a: T): R` 映射为 ArkTS 的 `foo: (a: T) => R`（箭头函数属性），而非 `foo(a: T): R`（方法声明）。在 ArkTS/TypeScript 中，箭头函数属性与方法声明在 `this` 绑定上有本质区别：
- 方法声明：`this` 绑定到调用对象
- 箭头函数属性：`this` 捕获定义时的上下文

当 ArkTS 侧实现该接口时，`this` 行为可能与预期不同，尤其是解构或传递方法引用时。

**严重程度**：高  
**影响范围**：§7

### 攻击 4-2：§7 接口继承的多继承冲突未讨论

§7 说"导出接口支持继承其他已标记 `@Interop[ArkTS]` 的接口"，但未讨论多接口继承时的成员冲突规则。例如两个父接口定义了同名但不同类型的 `prop`，仓颉侧按仓颉规则解决，但 ArkTS 侧的 `extends A, B` 如何处理？

**严重程度**：中  
**影响范围**：§7

### 攻击 4-3：§8 struct 映射为 interface 导致 ArkTS 侧无法用 instanceof 检查

struct 映射为 `interface` 而非 `class`，ArkTS 侧无法通过 `instanceof` 检查一个对象是否为某个 struct 类型。这在运行时类型判断时是重大限制。

**严重程度**：中  
**影响范围**：§8

### 攻击 4-4：§8 struct 深拷贝的嵌套引用场景未定义

若 struct 成员包含引用类型（如 `class` 实例），深拷贝是否递归拷贝引用类型成员？还是仅对值类型成员深拷贝、引用类型成员共享引用？"深拷贝"的精确语义未定义。

**严重程度**：高  
**影响范围**：§8

### 攻击 4-5：§9 枚举不支持字符串枚举

ArkTS/TypeScript 的 `enum` 支持字符串成员（`enum Color { Red = "RED" }`），但仓颉的枚举成员按声明顺序编号（数字枚举）。如果 ArkTS 侧期望字符串枚举，目前无法映射。这限制了与已有 ArkTS 代码的兼容。

**严重程度**：中  
**影响范围**：§9

### 攻击 4-6：§10.1 var 全局变量的 getter/setter 代理无原子性保证

§10.1 说 `var` 的读写通过胶水层的 getter/setter 代理完成。若多个 ArkTS 线程（如 Worker）或仓颉线程同时读写同一个全局 `var`，存在竞争条件。Spec 未讨论原子性或同步机制。

**严重程度**：高  
**影响范围**：§10.1

### 攻击 4-7：§10.1 const 内联值与运行时访问值可能不一致

§10.1 说基础类型 `const` 的值会在 `.d.ts` 中内联。若仓颉库发布新版本修改了 `const` 值，但 ArkTS 侧使用旧版 `.d.ts`（编译时已内联旧值），会导致编译时值与运行时值不一致。

**严重程度**：中  
**影响范围**：§10.1, 附录 D

## 二、裁判裁决（设计者角色）

| 编号 | 判定 | 理由 |
|------|------|------|
| 4-1 | **采纳** | 这是一个真实的语义差异。应在 §7 增加设计决策说明：选择箭头函数属性是为了与仓颉接口方法的语义一致（仓颉接口方法不绑定 `this`），并提示 ArkTS 侧实现者注意 `this` 行为。同时建议编译器在生成 `.d.ts` 时考虑使用方法声明语法，因为 ArkTS 侧实现接口时方法声明更自然。 |
| 4-2 | **部分采纳** | 多接口继承冲突在仓颉语言规范中已有规则（菱形继承解决方案）。ArkTS 侧的 `extends` 多继承冲突由 ArkTS 编译器检查。应增加简要说明："多接口继承时，成员冲突由仓颉编译器和 ArkTS 编译器各自在己方检查。" |
| 4-3 | **部分采纳** | 这是设计权衡。struct 映射为 interface 是为了匹配值语义——class 实例无法拷贝语义传递。应在 §8 增加注释说明 instanceof 缺失的影响和替代方案（使用鸭子类型/结构性检查）。 |
| 4-4 | **采纳** | 必须明确定义。正确语义应为："struct 的值类型成员递归深拷贝，引用类型（class）成员传递引用（两侧共享同一 class 实例）。"这与仓颉 struct 的赋值语义一致。 |
| 4-5 | **驳回** | 字符串枚举是 TypeScript 的特有功能，仓颉枚举无关联数据时自然为数字枚举。如需与 ArkTS 字符串枚举交互，应通过第二部分的 foreign 声明映射。两种语言的 enum 语义差异决定了映射限制。 |
| 4-6 | **采纳** | 全局 `var` 的并发安全是真实问题。但 ArkTS 主线程是单线程事件循环——并发来源于仓颉侧多线程。应明确说明：getter/setter 代理的调用最终在 ArkTS 线程上串行执行（基于《§13》的线程切换机制），仓颉侧并发调用通过任务投递串行化，因此不存在 ArkTS 侧的竞争条件。仓颉侧的并发安全由仓颉语言规则保证。 |
| 4-7 | **采纳** | 值内联与版本不一致的风险真实存在。应在 §10.1 或附录 D 增加风险说明，建议"发布版本更新 `const` 值时需重新生成 `.d.ts` 并重新编译依赖方"。 |

## 三、蓝军修改方案

### 修改 4-1：§7 增加 this 绑定语义说明
在接口成员映射表后增加：

> **关于方法映射形式的设计说明**：接口方法映射为箭头函数属性（`foo: (a: T) => R`），而非方法声明（`foo(a: T): R`），是为了避免 ArkTS/TypeScript 中方法声明的 `this` 绑定行为引入的语义偏差——仓颉接口方法不依赖 `this` 上下文。ArkTS 侧实现该接口时应注意：方法引用在解构或作为回调传递时，箭头函数形式的 `this` 绑定可能与方法声明形式不同。

### 修改 4-2：§7 增加多继承冲突说明
在接口继承说明后增加："多接口继承时，成员名称或类型冲突分别由仓颉编译器（仓颉侧声明）和 ArkTS 编译器（`.d.ts` 声明）各自检查。"

### 修改 4-3：§8 增加 instanceof 限制说明
在 struct 映射为 interface 的说明后增加：

> **注意**：由于 struct 映射为 `interface` 而非 `class`，ArkTS 侧无法使用 `instanceof` 进行类型判断。需要类型判断时可使用结构性检查（鸭子类型），即检查对象是否具备所需属性。

### 修改 4-4：§8 明确深拷贝语义
将"字段逐一拷贝"修改为更精确的表述："struct 的值类型成员（基础类型、其他 struct）递归深拷贝；引用类型成员（class 实例）传递引用，两侧共享同一对象实例。此行为与仓颉 struct 的赋值语义一致。"

### 修改 4-6：§10.1 增加并发安全说明
在 var getter/setter 代理说明后增加："全局 `var` 的 getter/setter 胶水代码在 ArkTS 运行时线程上串行执行，仓颉侧多线程并发调用通过线程切换机制（见 §13）自动串行化到 ArkTS 线程。仓颉侧对同一 `var` 的并发访问安全性由仓颉语言自身的并发规则保证。"

### 修改 4-7：§10.1 增加 const 内联版本风险提示
在 const 内联说明后增加注释："**版本兼容性注意**：当仓颉库更新 `const` 值时，需重新生成 `.d.ts` 文件并重新编译所有依赖该常量的 ArkTS 模块，否则编译时内联的旧值与运行时实际值不一致。"
