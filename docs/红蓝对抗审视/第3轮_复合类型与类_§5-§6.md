# 红蓝对抗审视 — 第 3 轮：§5 复合类型 & §6 类

**审视范围**：§5.1–§5.4, §6.1–§6.7
**日期**：2026-04-11

---

## 一、红军攻击意见（用户/架构师角色）

### 攻击 3-1：Array 拷贝语义缺少性能建议阈值或警告机制

§5.1 说明 `Array<T>` 以拷贝语义传递、逐元素转换，对大数组场景提到性能开销，但仅推荐使用 `JSArrayEx<T>` 而未给出编译器行为建议：编译器是否可以在检测到大数组模式时给出性能警告？是否有元素数量阈值建议？

**严重程度**：低  
**影响范围**：§5.1

### 攻击 3-2：函数类型回调的线程安全编译期规则不完备

§5.3 描述了三种场景的编译期处理（spawn 内直接调用、传递给非 Interop 函数、存储到全局变量），但未覆盖以下场景：
- 回调作为 `Array<() -> Unit>` 数组元素传递
- 回调嵌套：`callback: (() -> Unit) -> Unit` 内层回调的线程安全
- 回调被存储到导出类的字段中再由 ArkTS 侧调用

**严重程度**：中  
**影响范围**：§5.3

### 攻击 3-3：函数类型的可选形式 Option\<FuncType\> 的语义不充分

§5.3 末尾注释提到 `Option<(T1, ..., Tn) -> R>` 映射为 `((arg1: T1, ...) => R) | undefined`，但未讨论当 `None`（`undefined`）被传入仓颉侧后，仓颉代码尝试调用 `None` 函数时的行为——应明确是 `NullPointerException` 还是具体的互操作异常。

**严重程度**：中  
**影响范围**：§5.3, §4.5

### 攻击 3-4：§6.2 构造函数重载冲突示例不够直观

§6.2 示例展示了使用 Invisible 隐藏冲突构造函数的场景，但示例中的两个构造函数参数类型不同（`Float64` vs 无参），并不会产生冲突。真正的冲突场景（如 `init(Int32)` vs `init(Float64)` 都映射为 `constructor(number)`）的示例在 §6.5.5 才出现。§6.2 的"需满足条件"列表中提到冲突情况，但缺少直接示例。

**严重程度**：低  
**影响范围**：§6.2

### 攻击 3-5：§6.6 sealed open class 的警告策略不足

§6.6 说 `sealed open class` 导出时编译器给出警告，但 ArkTS 侧 `sealed` 语义不生效。仅给"警告"不足以防止跨语言继承安全性被破坏——应该提供更强的机制（如生成运行时检查，或默认禁止导出 sealed open 类，需显式 opt-in）。

**严重程度**：高  
**影响范围**：§6.6

### 攻击 3-6：§6.7 ArkTS 侧继承限制过多，实用性存疑

§6.7 列出 7 条限制（只能继承 open 类、只能重写 open 方法、仓颉侧不可见子类类型、子类新增成员不可访问、protected 不可访问、必须调用 super、多层混合继承受限）。如此多限制使得 ArkTS 侧继承仓颉类在实际项目中几乎不可用。规范应评估该功能的实用价值，或给出适用场景的明确指引。

**严重程度**：中  
**影响范围**：§6.7

### 攻击 3-7：§6.7 多态分派的性能开销未评估

§6.7 描述了 ArkTS 子类实例的多态分派："对象为 ArkTS 子类实例时通过胶水层分派到 ArkTS 侧重写实现"。每次多态调用都需要跨语言分派，性能开销可能显著。规范未讨论此开销，也未提供性能基线或优化建议。

**严重程度**：中  
**影响范围**：§6.7

### 攻击 3-8：§6.3 mut prop 的并发访问安全性未讨论

`mut prop` 在 ArkTS 侧为可读写属性，setter 调用会触发仓颉侧 `set` 方法。若多个仓颉线程同时操作同一个导出对象的属性，是否存在竞争条件？规范未讨论属性级别的线程安全。

**严重程度**：中  
**影响范围**：§6.3, §13

## 二、裁判裁决（设计者角色）

| 编号 | 判定 | 理由 |
|------|------|------|
| 3-1 | **驳回** | 性能阈值与具体平台和数据量相关，不属于语言规范的范畴。§5.1 已提供 `JSArrayEx<T>` 替代方案并说明了性能差异，足够指引开发者。编译器是否给出性能警告属于工具链实现决策。 |
| 3-2 | **部分采纳** | 回调作为数组元素和嵌套回调场景确实存在。但编译器的线程安全分析是尽力型（best-effort），无法穷举所有场景。应在 §5.3 增加兜底说明：编译器无法静态分析的场景一律通过 `JSFunc` 运行时线程切换机制保障。 |
| 3-3 | **采纳** | 应明确 `None` 回调的调用行为：仓颉侧对 `Option` 类型进行模式匹配后再调用，若直接对 `None` 调用则遵循仓颉 `Option` 的 `NoneValueException` 行为。 |
| 3-4 | **驳回** | §6.2 的 Invisible 示例用于展示隐藏功能本身（无参构造函数不导出），不是为了展示冲突。冲突示例在 §6.5 统一处理，避免重复。 |
| 3-5 | **部分采纳** | 完全禁止 `sealed open` 导出过于严格——部分业务场景需要此功能。但应将警告升级为：编译器默认报错，需通过显式选项（如 `@Interop[ArkTS, unsealedExport]`）确认后才允许导出。暂不引入新选项，但将警告措辞加强为"强烈建议不导出"。 |
| 3-6 | **部分采纳** | 限制确实较多，但均有技术原因。应在 §6.7 开头增加适用场景指引："ArkTS 侧继承仓颉类适用于仓颉侧提供基类框架、ArkTS 侧定制行为的场景（如 UI 组件回调、事件处理器扩展）。对于复杂继承需求，建议使用组合而非继承。" |
| 3-7 | **部分采纳** | 性能开销是实际关注点。应增加注释说明多态分派的额外开销（跨语言调用 + 线程检查），但具体数值因平台而异，不在规范中列出基线。 |
| 3-8 | **部分采纳** | 属性并发安全遵循仓颉语言自身的并发安全规则——导出对象的属性访问在仓颉侧仍受仓颉的线程安全机制管理。应在 §6.3 增加交叉引用指向 §13。 |

## 三、蓝军修改方案

### 修改 3-2：§5.3 增加兜底说明
在编译期检查表格后增加："对于编译器无法静态分析的回调使用场景（包括回调作为容器元素传递、多层嵌套回调等），运行时统一通过 `JSFunc` 线程切换机制保障安全：调用时自动投递到 ArkTS 绑定线程执行。"

### 修改 3-3：§5.3 增加 None 回调说明
在函数类型可选规则注释后增加："当 `Option<FuncType>` 值为 `None` 时，仓颉侧应在调用前检查（通过模式匹配或 `getOrThrow()`）。对 `None` 直接调用属于仓颉 `Option` 类型的空值解包行为，抛出仓颉标准的 `NoneValueException`。"

### 修改 3-5：§6.6 加强 sealed open 警告措辞
将"编译器给出警告"修改为："编译器给出警告，明确提示 ArkTS 侧无法强制执行 `sealed` 同包继承限制。**强烈建议避免将 `sealed open` 类导出到 ArkTS**；若确实需要导出，需在编译器配置中显式确认。"

### 修改 3-6：§6.7 增加适用场景指引
在 §6.7 开头增加："**适用场景**：ArkTS 侧继承仓颉类适用于仓颉侧提供基类框架、ArkTS 侧定制行为的场景（如 UI 组件回调基类、事件处理器扩展）。对于复杂继承层次或需要仓颉侧感知子类的需求，建议使用组合（composition）而非继承。"

### 修改 3-7：§6.7 增加性能注释
在多态分派描述后增加注释："**性能注意**：ArkTS 子类的多态分派需跨语言调用胶水层，相比仓颉原生多态调用有额外开销（涉及线程检查和跨语言调用路径切换）。在性能敏感的热路径上应避免频繁的跨语言多态调用。"

### 修改 3-8：§6.3 增加并发安全交叉引用
在 §6.3 成员属性表格后增加："多线程并发访问导出对象的属性时，线程安全性遵循仓颉语言的并发模型（见 §13）。"
