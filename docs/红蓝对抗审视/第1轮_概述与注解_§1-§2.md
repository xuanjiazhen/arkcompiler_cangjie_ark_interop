# 红蓝对抗审视 — 第 1 轮：§1 概述 & §2 @Interop[ArkTS] 注解

**审视范围**：§1.1–§1.4, §2.1–§2.6
**日期**：2026-04-11

---

## 一、红军攻击意见（用户/架构师角色）

### 攻击 1-1：特性支持矩阵遗漏 Rune 类型

§1.1 的"仓颉语言特性→ArkTS 侧表现形式"矩阵没有列出 `Rune` 类型。`Rune` 在 §3.1 中映射为 `number`，但在特性矩阵中未提及，读者无法从概述层面了解 `Rune` 的导出支持情况。

**严重程度**：中  
**影响范围**：§1.1

### 攻击 1-2：设计原则缺少"向后兼容性"与"可维护性"

§1.3 列出四条设计原则（类型安全、语义一致、兼容性、性能优先），但"兼容性"仅指与现有宏机制的兼容，并未涵盖 API 级别的**向后兼容策略**。对于一个互操作规范，API 演进与废弃策略至关重要——spec 应明确当未来类型映射规则变化时，旧导出声明如何迁移。

**严重程度**：低  
**影响范围**：§1.3

### 攻击 1-3：§1.1 表格"操作符重载 不支持"缺少变通方案指引

表格仅说"ArkTS 无对应语法"即止，但未指引开发者如何用命名方法替代操作符重载的等价功能（如 `operator func +` 可通过 `add()` 方法导出）。其他"不支持"项同理缺少变通建议。

**严重程度**：低  
**影响范围**：§1.1

### 攻击 1-4：@ArkTS 简写形式与 @Interop[ArkTS] 的推荐策略不明确

§2.1 引入 `@ArkTS` 简写但未给出推荐策略（新代码应优先用哪种形式？混用是否允许？团队规范如何选择？）。对比 §4.3 中 `JSStringEx`/`ArkString` 有明确推荐语句（"后续新代码推荐使用 `ArkString`"），注解简写此处缺少类似指引。

**严重程度**：低  
**影响范围**：§2.1

### 攻击 1-5：Invisible 对 enum 成员的语义存在歧义

§2.3 Invisible 表格显示枚举成员可被 Invisible 标记，但 §9 枚举章节说明枚举按声明顺序从 0 编号。若中间成员被 Invisible 隐藏，ArkTS 侧的编号是否跳过？例如 `Red=0, @Invisible Green, Blue=?`，Blue 是 1 还是 2？这一行为未定义。

**严重程度**：高  
**影响范围**：§2.3, §9

### 攻击 1-6：§2.5 "可导出类型"递归定义可能导致无限嵌套

§2.5 定义"可导出类型"包含"由可导出类型构成的 `Array<T>`、元组、函数类型"，这是递归定义。规范未明确递归深度限制。理论上 `Array<Array<Array<...>>>` 无限嵌套是否允许？编译器是否设置深度上限？

**严重程度**：中  
**影响范围**：§2.5

### 攻击 1-7：§2.6 多包合并模块的命名空间冲突未处理

§2.6 说非默认包封装在以包名命名的 `namespace` 中，但未定义包名与已导出声明名冲突时的处理策略。例如：默认包导出了一个名为 `math_utils` 的 class，同时有一个 `math_utils` 包的 namespace——这会产生命名冲突。

**严重程度**：中  
**影响范围**：§2.6

## 二、裁判裁决（设计者角色）

| 编号 | 判定 | 理由 |
|------|------|------|
| 1-1 | **驳回** | §1.1 表格列出的是语言特性级别（函数、类、接口等），不是类型级别。Rune 是基础数据类型，在 §3.1/§4 中已覆盖。表格粒度一致即可。 |
| 1-2 | **部分采纳** | 作为规范文档，API 向后兼容策略确实重要。但在设计原则中添加过重——建议在附录或版本记录部分增加"兼容性承诺"简要说明即可。 |
| 1-3 | **采纳** | 确实应该对不支持项提供变通方案的简要提示，提升规范的可操作性。 |
| 1-4 | **采纳** | 应增加推荐策略说明，与 `ArkString`/`JSStringEx` 的写法保持一致。 |
| 1-5 | **采纳** | 这是一个真实的语义缺陷。必须明确 Invisible 枚举成员时编号的处理规则。 |
| 1-6 | **部分采纳** | 递归嵌套在实践中由编译器资源限制自然截断。但规范应给出说明。建议添加"编译器可对嵌套深度设置实现定义的上限"的注释。 |
| 1-7 | **采纳** | 命名冲突是真实风险。应增加冲突检测与编译报错规则。 |

## 三、蓝军修改方案

### 修改 1-2：附录增加兼容性说明
在附录 F 版本记录后增加简要说明："后续版本更新遵循语义化版本规则，主版本号变更可能引入不兼容的类型映射调整，次版本号变更保持向后兼容。"

### 修改 1-3：§1.1 不支持项增加变通提示
在表格"操作符重载"行的说明列追加："可通过命名方法导出等价功能（如将 `operator func +` 实现为 `public func add(...)`）"。对 `extend` 行追加："可在导出类内部添加方法实现等价功能"。

### 修改 1-4：§2.1 增加推荐策略
在 `@ArkTS` 简写说明后添加注意："**推荐策略**：新代码推荐使用 `@ArkTS` 简写形式，以保持与 `@C` 风格的一致性。两种形式可共存于同一代码库。"

### 修改 1-5：§9 枚举章节补充 Invisible 编号规则
在 §9 枚举导出的注意事项中增加："被 `@Interop[ArkTS, Invisible]` 标记的枚举成员不参与导出，但其声明顺序编号保留——后续成员的编号不因隐藏成员而改变。例如：`Red=0, @Invisible Green(=1), Blue=2`。ArkTS 侧仅可见 `Red=0` 和 `Blue=2`。"

### 修改 1-6：§2.5 增加嵌套深度说明
在"可导出类型"定义后添加："编译器可对类型嵌套深度设置实现定义的上限，超出时报告编译错误。"

### 修改 1-7：§2.6 增加冲突检测规则
在多包合并模块规则中增加："当默认包的导出声明名称与非默认包的包名冲突时，编译器报告命名冲突错误，开发者需通过重命名消除歧义。"
