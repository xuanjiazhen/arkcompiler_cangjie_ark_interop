# 红蓝对抗审视 — 第 5 轮：§11 泛型 & §12 异常处理 & §13 并发与线程

**审视范围**：§11.1–§11.8, §12.1–§12.2, §13.1–§13.5
**日期**：2026-04-11

---

## 一、红军攻击意见（用户/架构师角色）

### 攻击 5-1：§11.2 JSInteropType 约束"自动蕴含"可能误导开发者

§11.2 说编译器自动对所有类型参数施加 `JSInteropType` 约束，开发者无需手动书写。但这意味着同一个泛型函数在仓颉内部调用和通过 ArkTS 调用时约束不同——仓颉内部调用不受 `JSInteropType` 约束。这种"双重身份"可能导致开发者写出仓颉内部能用但跨语言调用时报错的代码，且错误仅在 ArkTS 调用时才暴露。

**严重程度**：中  
**影响范围**：§11.2

### 攻击 5-2：§11.7 运行时类型检查机制的性能影响未量化

§11.7 描述了基于 typeof/instanceof/结构性检查的运行时推断机制，但未讨论性能影响。特别是"结构性检查"（检查所需属性和方法是否存在）对于大接口可能非常昂贵。仅说"性能敏感路径可生成特化胶水"缺乏具体判定标准。

**严重程度**：中  
**影响范围**：§11.7

### 攻击 5-3：§11.7 无法推断时"退回 JSValue 路径"的行为不明确

§11.7 说"无法推断时退回通用 `JSValue` 路径并在仓颉侧做最终校验"，但未定义 JSValue 路径的具体行为：以什么类型呈现给仓颉代码？校验失败的错误消息是否包含足够的调试信息？

**严重程度**：中  
**影响范围**：§11.7

### 攻击 5-4：§11.8 "不支持泛型枚举导出"理由不充分

§11.8 限制"不支持泛型枚举导出"的理由是"ArkTS enum 不支持泛型"。但仓颉本身也不支持泛型枚举——这条限制是多余的。如果仓颉不支持泛型枚举，此条应删除或标注为"不适用（仓颉语言无此特性）"。

**严重程度**：低  
**影响范围**：§11.8

### 攻击 5-5：§12.1 异常映射仅有 3 种类型，缺少 SyntaxError/URIError 等

§12.1 将仓颉异常映射为 `Error` 和 `BusinessError` 两种 ArkTS 错误类型。但 ArkTS/JavaScript 还有 `SyntaxError`、`URIError`、`ReferenceError`、`EvalError` 等，若仓颉侧需要抛出这些特定类型的错误给 ArkTS 侧，当前映射不支持。

**严重程度**：低  
**影响范围**：§12.1

### 攻击 5-6：§12.2 错误码 34300001 INDEX_OUT_OF_RANGE 在主文中从未被引用

§12.2 的错误码表列出了 `INDEX_OUT_OF_RANGE`（34300001），但在整个 spec 正文中没有任何章节引用该错误码的触发场景。其他四个错误码都有明确的"详细章节"列，但 34300001 没有。

**严重程度**：高  
**影响范围**：§12.2, 附录 A

### 攻击 5-7：§13.2 Future\<T\> 的 T 不允许为延迟转换类型的限制过于严格

§13.2 禁止 `Future<T>` 的 `T` 为 `JSStringEx`、`JSArrayEx`、`JSHashMapEx` 等延迟转换类型，理由是"异步执行可能跨越引用的线程和生命周期边界"。但如果仓颉侧在异步完成时将延迟转换类型转换为普通类型再返回，这一限制就不必要。规范是否可以允许异步函数内部使用延迟转换类型，仅限制返回值类型？

**严重程度**：中  
**影响范围**：§13.2

### 攻击 5-8：§13.5 循环引用导致内存泄漏无解决方案

§13.5 注意事项中仅说"避免循环引用"，但未提供检测或打破循环引用的机制。对于复杂的互操作应用，开发者很难保证不形成循环引用。应至少提供弱引用或手动释放的 API 建议。

**严重程度**：高  
**影响范围**：§13.5

### 攻击 5-9：§13.3 编译器对回调逃逸到可逃逸作用域的检测复杂度过高

§13.3 说"当回调被存储到可逃逸作用域（如实例字段）时，编译器生成线程安全的包装闭包"。但逃逸分析的精度有限——回调可能通过多层间接引用逃逸。编译器是否会保守地对所有回调类型参数都生成包装闭包？若是，则性能开销不可忽视。

**严重程度**：中  
**影响范围**：§13.3

## 二、裁判裁决（设计者角色）

| 编号 | 判定 | 理由 |
|------|------|------|
| 5-1 | **部分采纳** | 双重身份是设计选择——与 C 互操作中 `CType` 的行为一致。但应增加注释提醒开发者注意此差异，建议在测试中覆盖 ArkTS 调用路径。 |
| 5-2 | **驳回** | 性能量化属于工程实现范畴，不属于语言规范。规范已明确性能敏感路径可特化的方向。 |
| 5-3 | **采纳** | JSValue 退化路径需要更明确的描述。应说明：退为 JSValue 后仓颉侧收到 `JSObject` 类型值，`TYPE_MISMATCH` 异常消息包含期望类型和实际 typeof 结果信息。 |
| 5-4 | **采纳** | 如果仓颉本身不支持泛型枚举，此限制条目冗余。应修改为"不适用（仓颉语言不支持泛型枚举）"或直接删除。 |
| 5-5 | **驳回** | §12.1 定义的是 仓颉异常→ArkTS 错误 的映射。仓颉标准异常体系中没有 SyntaxError/URIError 对应物，因此不需要映射。若开发者需要特定 ArkTS 错误类型，可通过 `BusinessException` + 错误码实现。 |
| 5-6 | **采纳** | `INDEX_OUT_OF_RANGE` 应有明确的触发场景引用。该错误码用于 `JSArrayEx` 的下标访问越界等场景。应在 §16.2 JSArrayEx 描述或 §12.2 中补充引用。 |
| 5-7 | **驳回** | 限制是对返回值类型的约束。异步函数内部使用延迟转换类型不受限——限制仅针对 `Future<T>` 的 `T`，即最终传回 ArkTS 的类型。规范已明确是返回类型约束。 |
| 5-8 | **部分采纳** | 循环引用是 GC 互操作的经典难题。完整解决方案（弱引用 API）超出本版本范围，但应增加工具向指引：建议使用弱引用容器（若互操作库提供）或在应用层设计单向引用拓扑。 |
| 5-9 | **部分采纳** | 编译器应采用保守策略——对无法确定安全性的回调参数统一生成线程安全包装。性能开销由包装层承担，安全性优先。应在 §13.3 说明此保守策略。 |

## 三、蓝军修改方案

### 修改 5-1：§11.2 增加注意提示
在自动蕴含约束说明后增加："**注意**：同一泛型函数在仓颉内部调用时不受 `JSInteropType` 约束检查，仅在 ArkTS 调用时生效。建议在测试中覆盖 ArkTS 调用路径，确保所有类型参数在跨语言场景下满足约束。"

### 修改 5-3：§11.7 明确 JSValue 退化路径行为
在"退回通用 `JSValue` 路径"后修改为："退回通用路径后，仓颉侧以 `JSObject` 类型接收值，在实际使用时按目标类型做校验与转换。校验失败时抛出 `TYPE_MISMATCH` 异常，错误消息包含期望类型名与实际 `typeof` 结果。"

### 修改 5-4：§11.8 修正泛型枚举限制表述
将"不支持泛型枚举导出 | ArkTS enum 不支持泛型"修改为："不适用 | 仓颉语言不支持泛型枚举"。

### 修改 5-6：§12.2 补充 INDEX_OUT_OF_RANGE 引用
在 §12.2 错误码表格 34300001 行的"详细章节"列填入："16.2 JSArrayEx 下标访问"。同时在 §16.2 JSArrayEx 描述中增加："下标越界时抛出 `INDEX_OUT_OF_RANGE`（34300001）异常。"

### 修改 5-8：§13.5 增加工程建议
在循环引用注意后增加："**工程建议**：在互操作应用设计中，建议保持仓颉→ArkTS 的单向引用拓扑，避免双向持有。若业务需要双向引用，考虑使用事件/回调机制替代直接对象引用，或在引用不再需要时主动调用释放 API 解除引用。"

### 修改 5-9：§13.3 说明保守策略
在编译期检查表格后增加："当逃逸分析无法确定回调的线程安全性时，编译器采用保守策略——统一生成线程安全的包装闭包以保障正确性。此策略可能引入额外的包装开销，在性能敏感场景中建议开发者保持回调的局部使用以利于编译器优化。"
